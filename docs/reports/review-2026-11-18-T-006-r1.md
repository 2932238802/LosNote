## 4. 缺陷清单

### [P1] stale 锁清理路径没有串行化，两个实例可同时通过锁

- 位置：`update.sh:121-159`（重点 `:146-157`：`mv` → `rm -rf` → `mkdir`）；清理 `:161-166`
- 问题：两个进程同时遇到 stale 锁时都判定“过期”，各自 `mv`/`rm`/`mkdir`。A 完成清理并建新锁后，B 的 `mv` 仍可能把 A 的新锁移走、删除并重建；两个进程都认为拿到锁并继续。`mv` 只保证单次重命名原子，不保证“检查 stale → 清理 → 重建”序列原子。`cleanup_lock` 只检查内存 `LOCK_OWNER_PID`，不校验磁盘 `pid` 文件，A 退出时可能删除 B 的锁。
- 触发：上次执行被 SIGKILL/断电留下 stale 锁，随后两个实例几乎同时启动（手动 + cron/重试/自动化）。
- 影响：两个实例可同时执行 L2 备份与 L3 `up --build --force-recreate`；新版备份 JS 会删除所有 `losnote-*.db.tmp`，可能删掉另一个实例正在写的临时文件，导致对方备份失败；两次重建可能冲突、造成重复停机；A 的 `cleanup_lock` 还可能移除 B 的锁，让第三个实例进入。数据卷不会被脚本删除，但 `AC-002-7` 被破坏。
- 证据：3/3 可控复现，两个不同脚本 PID 都到达 `docker compose version`；自然同时启动 10 次 0/10。
- 建议：增加独立原子 breaker 锁（如 `mkdir "$LOCK_DIR.break"`），只有 breaker 持有者能重新读取/清理 stale 主锁；`cleanup_lock` 删除前校验 `cat "$LOCK_DIR/pid"` 等于 `$$`。可进一步用随机 nonce/进程启动时间；或取消自动清理，改为提示手动删除。补回归：两个实例同时面对 stale 锁，只允许一个到达 `compose version`。
- 置信度：高（代码路径与 3/3 复现）；自然触发频率低。

### [P3] 锁回退路径仍有本地 DoS / PID 复用 / TMPDIR 差异风险

- 位置：`update.sh:101-145`
- 问题：`/run/lock` 不可写时回退 `${TMPDIR:-/tmp}`；本地用户可预创建锁目录/`pid` 文件；不同 TMPDIR 可绕过互斥；PID 复用会误判活跃；无 PID 10 秒阈值可能误清 SIGSTOP 的活跃锁。
- 建议：固定私有锁基目录（`/run/lock` root 专属或 `$HOME/.cache` 700），不依赖 TMPDIR；pid 记录启动时间/命令行摘要；或要求 root 并在文档写明。

### [P3] 备份目录 `chmod 0700` 在既有 root 属主目录上可能失败并阻塞更新

- 位置：`update.sh:327-328`
- 问题：备份 JS 以容器内 `node` 用户运行；若 `/data/backups` 属主是 root，`chmod` EPERM，备份失败并阻止重建。
- 建议：chmod 失败降级为警告并继续（或仅在新建目录时设置），T-008 检查卷属主。

### [P3] `[::]` 归一为 `127.0.0.1` 假设双栈，IPv6-only 发布会误判

- 位置：`update.sh:412-414`
- 问题：若宿主只发布 IPv6 且服务不监听 IPv4，L5 健康检查失败。
- 建议：先试 127.0.0.1，失败再试 `[::1]`/原始地址。
