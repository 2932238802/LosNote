## 1. P1-1 根因与修复

### 根因

原 `mkdir` + breaker 方案在 WSL2 的 tmpfs 上无法保证互斥：本机实测并发 `mkdir` 同一个路径，100 次中有 **72 次两个进程都返回成功**（`mkdir -m 700 /run/lock/...`）。因此即使 breaker 逻辑本身正确，两个实例仍可能同时拿到锁。这是测试环境的文件系统行为，不是 shell 逻辑能补救的。

### 修复

放弃 `mkdir/PID/stale/breaker` 清理路径，改用内核 `flock`（原任务第 3 条允许“flock 或 mkdir 锁”）：

- `flock -n -E 75 -o "$LOCK_FILE" env LOSNOTE_UPDATE_LOCKED=1 bash "$SELF" ...`
  - `-n`：非阻塞，第二实例立即失败；
  - `-E 75`：锁冲突固定退出 75，与脚本自身退出码区分；
  - `-o`：执行子脚本前关闭锁 fd，脚本及其 `docker` 子进程不继承锁；
  - 由 `flock` 监督进程持有锁，子脚本退出（含 SIGKILL）后内核自动释放，没有 stale 锁。
- 锁文件路径：
  - 优先 `/run/lock`（root 专属）；
  - 不可写时用 `$HOME/.cache/losnote-update`（`0700`）；
  - **不再回退 `/tmp`**，不依赖 `TMPDIR`。
- 锁文件：`losnote-update-<脚本目录 cksum>.lock`，`0600`；打开前 `[ -L ]` 拒绝符号链接。
- `--help` / `--bogus` 在取锁前处理，不会因为锁冲突挡住帮助。

## 2. 验收证据

### P1-1：预置 stale 锁 + 两个实例并发

按评审描述预置旧版 `LOCK_DIR`（`.d`，`pid=999999`），PATH 中放慢 `mv`（1.5 秒），假 docker 在 `compose version` 记录调用者 PID：

| 轮次 | compose version 调用者数 | 结果 |
|---|---|---|
| 5 次（慢 `mv` + 睡眠假 docker） | 每次 1 | 5/5 只允许一个实例通过 |
| 30 次（睡眠假 docker，无慢 `mv`） | 每次 1 | 30/30 只允许一个实例通过 |

- 获胜实例输出：`→ L1 代码：前置检查` → `docker compose v2 不可用`（假 docker 故意失败以结束测试）。
- 失败实例输出：`× [L1 代码] 已有另一个 update.sh 正在执行（...lock），本次退出。` + `前置检查失败，未改动工作区，无需回滚。`
- 旧 `.d` stale 目录不再参与互斥；`flock` 文件没有 PID/stale 清理路径，因此不存在“两个实例同时清理 stale 锁”的竞态。

### 普通并发（无 stale 锁）

以睡眠 1 秒的假 docker 保持获胜实例存活，50 次同时启动两个实例：

- `compose version` 调用者数每次均为 1，`multi_callers=0/50`。
- 第二实例输出锁冲突并退出 1。

### 其他锁场景

| 场景 | 结果 |
|---|---|
| 活跃锁（外部 `flock` 持有） | 第二实例立即退出 1，提示“已有另一个 update.sh 正在执行” |
| 杀死持有者（`flock -o` 进程） | 下一次运行成功取锁并到达 `compose version`（`compose_calls=1`） |
| 符号链接锁文件 | `× [L1 代码] 锁文件是符号链接，拒绝使用`，退出 1 |
| 连续两次执行 | 两次都取锁成功，各 `compose_calls=1`；执行后 `flock -n` 可立即再次获得 |
| 缺 `.env` | 取锁成功后进入 L1，输出 `× [L1 代码] 缺少 .env...` + 无需回滚，退出 1 |

锁文件执行后保留、权限 `600`。这是有意设计：删除正在被等待的 flock 文件会引入 inode 替换竞态；保留文件不持有锁，不影响下一次执行。

## 5. 风险与说明

- 新增对 `flock` 的硬依赖（util-linux，Ubuntu/Debian 默认安装）；缺失时 `fail_precheck` 明确报错。
- 锁文件保留在 `/run/lock`（重启清空）或 `$HOME/.cache/losnote-update`（`0700`）；文件本身不持有锁。
- 旧版 `.d` / `.break` 目录不再使用；如服务器上仍有，可手动删除，不影响新脚本。
- `flock -o` 保证脚本与 docker 子进程不继承锁 fd；顶层包装进程被单独 SIGKILL 时，flock 监督进程与更新子进程会继续运行（更新未结束，锁应继续持有）；更新子进程退出或被一起杀掉时锁立即释放。
