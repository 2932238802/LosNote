## 1. P2 修复：合并预检与正式锁，消除 TOCTOU

### 原问题

r3 的 wrapper 先 `exec 9>>` 试锁、关闭 fd 9，再另起 `flock -n -E 75` 正式锁。两步之间锁被释放，两个实例可能都在正式锁阶段失败，出现“零 worker / 静默 exit 75”。

### 修复

改为**一次取锁、fd 9 全程保持打开**：

1. 选定锁文件后 `exec 9>>"$candidate"`，随后 `flock -n 9`。
2. 成功时不关闭 fd 9；`export LOSNOTE_UPDATE_LOCKED=1` 后 `bash "$SELF" ... &` 启动 worker，wrapper `wait`。
3. worker 通过 fork/exec 继承同一个 open file description，因此：
   - 只杀 wrapper/父进程：worker 仍持有 fd 9，锁不释放，第二实例被拒绝；
   - worker 退出（含 SIGKILL）：fd 关闭，内核释放锁；
   - worker 自身 `exit 75`：wrapper 原样 `exit 75`，不再有“75 = 锁冲突”的误判。
4. 删除 `flock -n -E 75`、关闭 fd 9、re-check 后静默 `exit 75` 的整条路径。
5. worker 完成锁块后 `unset LOSNOTE_UPDATE_LOCKED`，子进程不继承内部变量。

关键位置：`update.sh:107-185`（`exec 9>>` 在 159，`flock -n 9` 在 171，`unset` 在 185）。

### 附带发现并修复

调试 50 轮并发时发现：`exec 9>>"$candidate" 2>/dev/null` 会把**整个 shell 的 stderr 永久重定向到 /dev/null**，导致失败方静默、获胜方失败信息丢失。已去掉该重定向，并加注释说明 `exec` 只应做 fd 重定向，不能在这里重定向 shell 的 stderr。修复后 50/50 每轮都有一方输出“已有另一个 update.sh 正在执行”。

## 5. 风险与说明

- wrapper 与 worker 是两个进程，共享同一个锁 fd：
  - 只杀 wrapper：worker 继续并持有锁（符合本轮验收）；
  - 只杀 worker：wrapper 的 `wait` 返回后退出，锁释放；
  - 更新期间 worker 的 docker/git 子进程会继承锁 fd；它们短命，worker 被杀后锁会在它们退出后释放（已接受的 trade-off）。
- 锁文件保留在 `/run/lock` 或 `$HOME/.cache/losnote-update`；文件本身不持有锁，保留以避免 flock 文件的 inode 替换竞态。
- `/run/lock` 世界可写时优先 `$HOME/.cache/losnote-update`（0700）；两者都不可用则明确失败，不回退 `/tmp`。
- 外部设置 `LOSNOTE_UPDATE_LOCKED=1` 可绕过锁；`--help` 已标注仅供内部使用，本轮不扩大处理。
- 旧版 `.d` / `.break` 目录不再使用；可手动删除，不影响新脚本。
