## CR-001 网页端「开始 / 重新抽题」反复出现同一题

- 类型：缺陷
- 问题与价值：网页复习页点击「开始 / 重新抽题」多次，仍反复显示同一道题。服务端提交版按 `next_review ASC, created_at DESC` 确定性排序，未评分时首题恒定；用户会误以为抽题失效或题库只有一题。不做会持续影响网页复习体验，并让“随机抽题”承诺失效。
- 目标用户与场景：使用网页端复习、题库中有 ≥2 道到期题、连续点击「开始 / 重新抽题」的用户。
- 成功指标：
  - 基线：6 道到期题、连续取首题 5 次 → `n6 n6 n6 n6 n6`（2026-11-18 内存库复现）。
  - 目标（由用户“尽可能随机、不能感受到规律”转写，具体阈值待 G1 确认）：
    ① 到期题 > 1 时，连续两次点击「开始 / 重新抽题」不得显示同一题；
    ② 到期题 ≥ 5 时，连续点击 20 次至少出现 3 道不同题；
    ③ 人工观测不出现固定顺序或短周期循环。
  - 可观察验收场景：题库准备至少 5 道到期题 → 打开 `https://losnote.los-theseus.site/` 的「复习」→ 连续点击 20 次「开始 / 重新抽题」并记录首题 → 至少出现 3 道不同题，且没有连续两次相同，控制台 0 报错。
- 范围：网页端抽题交互（`web/src/views/QuizView.vue`）、服务端到期题排序（`server/src/notes.js: listDue`）、对应自动化测试（`server/test/`、`web/e2e/`）。
- 非目标：SRS 算法与三档评分逻辑；安卓端 `QuizFragment` 的抽题；题库内容与栏目筛选规则；鉴权与同步协议。
- NFR：
  - 性能：适用。`ORDER BY RANDOM()` 需对到期结果集排序，题量上限 1000（`server/src/notes.js:365`）；目标 1000 题时接口响应 < 100ms，待实测。
  - 安全：不适用（不改鉴权、不新增输入面）。
  - 隐私与数据保留：不适用（不新增采集与存储）。
  - 兼容性：适用。`GET /api/quiz/due` 响应结构不变，仅顺序变化；旧网页端无需改动也能工作。
  - 可观测性：不适用（无新增后台任务与告警面）。
  - 成本：不适用（不增加外部调用与存储）。
- 约束与依赖：
  - 用户观测环境为公网部署 `https://losnote.los-theseus.site/`（nginx 反代，HTTPS）。2026-11-18 只读检查：站点 200、`/api/health` 200、未授权 `/api/quiz/due` 401；服务端源码版本无法从外部确认，`docs/deploy.md:168` 记录为 `3dfb6e2`。
  - 线上实例早于当前 `HEAD`；即使代码修复，也需要重新部署/重启才生效。
  - 工作区已有未提交改动把排序改为 `ORDER BY RANDOM()`，但无测试、未部署；是否采用由开发阶段评估。
- 风险与未知：
  - 若到期题只有 1 道，随机无意义（`A-003`）。
  - 仅服务端随机仍有概率连续相同（复现中 `RANDOM()` 版两次 `n4`）；用户要求“不能感受到规律”，因此需要前端兜底，不能只依赖服务端随机。
  - 大题库下 `ORDER BY RANDOM()` 的性能未实测。
- 选项：
  - **A. 完整修复**：服务端随机 + 前端在到期题 > 1 时避免与上一次相同 + 服务端/浏览器测试。代价：前后端各改一处，新增测试；收益：稳定满足“连续多次不同”。
  - **B. 拆小**：先只改服务端 `ORDER BY RANDOM()` 并部署验证；前端兜底留到下一轮。代价：仍有小概率连续相同。
  - **C. 先 spike / 排查**：只确认线上是否跑旧版本、未提交改动是否生效，再决定是否改代码。代价：最快定位；但若目标包含“连续不同”，仍需回到 A/B。
  - **D. 缓办**：等待条件：确认只是部署未更新（`A-001`）。
  - **E. 不做**：理由需用户给出；不推荐，因为“随机抽题”是页面明确承诺。
- 推荐：**A**。理由：用户要求“尽可能随机、不能感受到规律”，仅改服务端仍有可观察的连续重复；前端兜底（到期题 > 1 时避开上一题）才能稳定满足验收场景。主要风险：大题库下随机排序性能，需要在实现阶段实测。
- 关联需求/任务：`R-001 v1`；`T-001`–`T-004`（见 `04-tasks.md`）
- 状态：**已确认**（2026-11-18，用户选择 **A. 完整修复**）
- G0 结论：用户选择 A；G1 已由用户确认（2026-11-18），进入 G2 开发。

## CR-002 新增 `update.sh` 一键拉取与重建（服务器更新入口）

- 类型：新功能（运维工具）
- 问题与价值：服务器更新目前靠手工 `git pull` + `docker compose up -d --build`。2026-11-18 实际发生 `origin` 指向本地镜像 `/opt/git/losnote.git`，`git pull` 显示 Already up to date，但服务器 HEAD 仍是旧提交，容易误判“已经更新”。脚本把「拉新 → 备份 → 重建 → 验证」标准化，失败即停并给出回滚信息。
- 目标用户与场景：在 Linux 服务器 `/opt/losnote` 维护部署的管理员，每次发布后执行一次。
- 成功指标：
  - 一次执行结束后能证明运行的容器来自 `origin/main` 的最新 commit（HEAD == origin/main，容器启动时间晚于构建，健康检查与前端指纹通过）。
  - 失败时不带着旧代码或旧镜像重启；退出码非 0 并打印日志与回滚信息。
  - 基线：手工操作无校验，已出现“pull 显示最新但实际未更新”的误判。
- 范围：根目录 `update.sh`；Docker Compose 部署；git 快进；SQLite `VACUUM INTO` 备份；`docker compose up -d --build`；容器启动时间与 `/api/health` 校验；前端资源指纹；失败日志与回滚提示；并发锁。
- 非目标：不做 CI/CD 自动触发；不支持 systemd/pm2 多模式；不改应用代码；不自动处理 git 分叉（不 `reset --hard`）；不管理 HTTPS/证书；不删除数据卷。
- NFR：
  - 安全：不读取/打印 `LOSNOTE_TOKEN`；不删除 `losnote-data`；备份文件权限合理。
  - 性能：脚本自身开销 <1s；主要耗时是 Docker 构建；备份为单文件快照。
  - 兼容性：bash 4+、Docker Compose v2；兼容当前 SSH origin 与本地镜像 origin；Linux 服务器。
  - 可观测性：分阶段输出；失败时打印 `docker compose logs --tail=100` 与失败阶段。
  - 隐私/成本：不适用（不新增采集与外部服务）。
- 约束与依赖：`Dockerfile` 多阶段构建，`web/dist` 在镜像内；数据卷 `losnote-data`；服务器可能无法直连 GitHub（脚本只依赖已配置好的 `origin`）；本机无 Docker，端到端验证须在服务器执行（`T-008`）。
- 风险与未知：备份失败、构建失败、健康检查失败；备份占磁盘（需保留策略）；origin 不可达；镜像重建期间短暂停机。
- 选项：
  - **A. 稳健版**（已选）：前置检查 + 快进 + 备份 + 重建 + 启动时间/健康/前端指纹 + 失败日志/回滚提示 + 并发锁。
  - B. 最小版：`git pull --ff-only` + `docker compose up -d --build` + health。
  - C. 完全对齐 Vesta：移植 L1–L5、`--no-pull/--skip-build`、docker/systemd/pm2 多模式。
  - D. 暂缓。
- 推荐：**A**。理由：本次已发生“pull 显示最新但实际未更新”的真实误判；稳健版用可验证证据替代人工判断。
- 关联需求/任务：`R-002 v1`；`T-006`（实现）、`T-008`（服务器验收）。
- 状态：**已确认**（2026-11-18，用户选择 **A. 稳健版**）。

## CR-003 网页端 favicon（新矢量标记）

- 类型：新功能 / 品牌改进
- 问题与价值：`web/index.html` 目前没有 icon 链接，浏览器标签页显示默认空白图标；收藏或多标签时难以辨识，也与 App 已有图标不一致。
- 目标用户与场景：使用网页端（浏览器标签页、收藏夹）的用户。
- 成功指标：
  - 打开 `https://losnote.los-theseus.site/` 后，标签页显示新图标。
  - `GET /favicon.svg`、`/favicon.ico`、`/favicon-32.png` 均返回 200，MIME 正确。
  - 16×16 下仍能辨认“纸卡 + 星”轮廓，无糊成一团的细线。
  - 页面不新增任何外部请求。
- 范围：`web/public/` 下的 favicon 静态资源；`web/index.html` 的 `<link rel="icon">`；新矢量标记（简化纸卡 + 金色星，沿用品牌色）；SVG + ICO/PNG 回退。
- 非目标：Apple touch icon；PWA manifest / 192/512 安装图标；Android 启动图标改动；动画 favicon；图标设计系统重构。
- NFR：
  - 性能：全部图标资源合计 <20KB；不新增 JS。
  - 安全：无脚本、无外部 CDN。
  - 隐私与数据保留：不适用。
  - 兼容性：现代浏览器用 SVG；旧浏览器回退 ICO/PNG；深浅色标签页均可见。
  - 可观测性/成本：不适用。
- 约束与依赖：Vite 的 `public/` 会原样复制到 `web/dist`；Docker 镜像包含 `web-dist`；本机无 ImageMagick/Pillow，PNG/ICO 需用 Node 或现有 PNG 生成。
- 风险与未知：16px 细节丢失；浏览器对 favicon 强缓存；深色标签页对比度；设计方向需确认（`A-005`）。
- 选项：
  - A. 复用 Android 图标；B. 新做矢量标记（已选）；C. 纯字母标 “LN”。
  - 范围：仅标签页 favicon（已选）/ 加 Apple 主屏 / 加 PWA manifest。
- 推荐：**B + 仅标签页 favicon**。理由：矢量为小尺寸优化，能保持与 App 同一套品牌元素；不引入 PWA 的额外范围。
- 关联需求/任务：`R-003 v1`；`T-007`。
- 状态：**已确认**（2026-11-18，用户选择 **新矢量标记 + 仅标签页 favicon**）。
